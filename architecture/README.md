# Linux Sticky Memo 아키텍처 맵

현재 Rust/GTK 구현의 구조를 단계별로 탐색한다. 배포 시스템의 컨테이너(Docker)와 C4의 Container 개념은 다르다. 다이어그램은 Mermaid flowchart이며 C4 수준과 경계를 노드에 명시한다.

| 수준 | 질문 | 문서 |
|---|---|---|
| C1 · Context | 누가 사용하고 외부 환경과 어떻게 연결되는가? | [시스템 맥락](01-context.md) |
| C2 · Container | 실행 프로그램과 데이터 저장소는 무엇인가? | [실행·저장 단위](02-containers.md) |
| C3 · Component | 앱 내부 책임과 의존 관계는 무엇인가? | [UI 컴포넌트](03-ui-components.md), [저장 컴포넌트](03-persistence-components.md) |
| C4 · Code | 구현의 어느 지점으로 들어가야 하는가? | [UI 코드](code/ui.md), [저장 코드](code/persistence.md), [기반 코드](code/platform.md) |

C4는 선택 사항이다. 이 프로젝트에서는 수동 클래스 다이어그램을 복제하지 않고 실제 소스와 함수로 연결한다. 클래스 상속이 없는 Rust 모듈 구조를 클래스 계층으로 바꾸어 설명하지 않는다.

## 읽는 순서와 유지 기준

처음에는 C1 → C2 → 관심 있는 C3 → 해당 C4 코드 링크 순으로 읽는다. UI 변경은 UI 맵, 저장 변경은 저장 맵에서 출발한다. 두 C3 뷰의 공통 노드는 같은 구현을 가리킨다.

코드가 동작의 원본이며, 이 문서는 책임·경계·관계를 설명하는 탐색용 맵이다. 실행 단위가 바뀌면 C2, 책임이나 의존성이 바뀌면 해당 C3, 파일·함수 위치가 바뀌면 해당 코드 라우팅만 갱신한다. 문서별로 구현 세부를 중복 기재하지 않는다.

설치·검증은 [프로젝트 README](../README.md), 리팩토링 근거는 [REFACTORING](../REFACTORING.md)을 따른다. 계획 문서의 미래 요구를 현재 구현으로 표시하지 않는다.
